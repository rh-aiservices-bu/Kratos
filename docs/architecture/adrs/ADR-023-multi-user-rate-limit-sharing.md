# ADR-023: Multi-User Rate-Limit Sharing via ServiceAccount-Minted Identities

## Status

Accepted

## Context

Every existing rate-limit/subscription scenario (`rate_limit_validation`, `multi_key_load`, `rate_limit_priority_precedence`) tests **one caller** — the harness's own ServiceAccount — provisioning N keys. `docs/architecture/empirical-verification-checklist.md`'s §5 ("Next Up") flags an open question this can never answer: a live `TokenRateLimitPolicy` uses `counters: [{expression: auth.identity.userid}]`, which hints that quota may be tracked **per distinct caller identity**, not pooled across everyone sharing a `MaaSSubscription`. With only one identity available, the harness has no way to tell "two users, one subscription" apart from "one user, two keys."

This directly overlaps with a previously-documented, currently-broken scenario: ADR-018's Update section shows `access_denied_no_policy.yaml` reverted from Verified to Gap because `provision_api_key`'s `subscription` param only *disambiguates among subscriptions the caller already qualifies for* — it can't force-bind an ineligible caller. The Update's own "path to an actual fix, not yet built" is: mint a throwaway ServiceAccount via the Kubernetes TokenRequest API and bind `spec.owner.users` directly to its fully-qualified username, rather than relying on group membership. That mechanism is exactly what this ADR builds — as a byproduct, not its primary goal, since fixing `access_denied_no_policy` itself is out of scope here.

## Decision

**New task module** `harness/tasks/identity.py`:

- `CreateUserTask` (`create_user`): mints `count` throwaway `ServiceAccount`s in the harness's own `maaspal` namespace, then a `TokenRequest`-issued token for each (`CoreV1Api.create_namespaced_service_account`/`create_namespaced_service_account_token`). This is the only identity-minting mechanism buildable from this harness's existing RBAC model — a real OpenShift `User`/`Identity` needs IdP/OAuth integration the harness has no access to, and was never considered viable (same reasoning the checklist already applied to its own §1). Each SA's username (`system:serviceaccount:<ns>:<name>`) is confirmed live (ADR-018's Update, direct `TokenReview`) to be a real, directly-matchable identity against `MaaSSubscription.spec.owner.users[]`. Results land in `shared_state["users"]` as a list of `{name, namespace, username, token}`.
- `ProvisionKeysForUsersTask` (`provision_keys_for_users`): iterates `shared_state["users"]`, calling `POST /maas-api/v1/api-keys` authenticated with **each user's own token**, not `ctx.sa_token` — so the resulting key is genuinely minted as that caller, not the harness. All keys pin to one shared `subscription` param. Appends to `shared_state["api_keys"]` (the same list `send_requests`'s `key_pool` already reads) with an added `owner_username`. Reuses `ProvisionApiKeyTask`'s `key_provision_checks` counters shape unchanged, so existing assertion patterns work without new plumbing.

**`harness/tasks/subscription.py` changes**, both additive/backward-compatible:

- Bug fix: `owner_groups = self.params.get("owner_groups") or _DEFAULT_OWNER_GROUPS` silently replaced an explicit `owner_groups: []` with the default (`[] or X` → `X`). Changed to the two-arg `self.params.get("owner_groups", _DEFAULT_OWNER_GROUPS)` in all three tasks that shared this pattern (`ApplyRateLimitSubscriptionTask`, `ApplyPriorityTestSubscriptionsTask`, `ProvisionSubscriptionsDistributedTask`) so an explicit empty list actually narrows the subscription's blast radius, rather than silently reopening it to every `system:authenticated` caller on the cluster. No existing scenario passes an empty list, so this changes nothing for them.
- New `owner_users_from_shared_state` param on `ApplyRateLimitSubscriptionTask`: when set to a `shared_state` key (e.g. `"users"`), reads that list and appends each entry's `username` to `owner_users`. This is necessary, not a nicety — `${config.x}` substitution resolves once at scenario load, and `${harness.x}`/`${baseline.x}` substitution (`harness/runner.py`) exists only for assertion evaluation, never for task `params:`. A dynamically-minted identity's username literally cannot be spelled out in YAML. An **explicit** param naming the `shared_state` key was chosen over an implicit "if `shared_state["users"]` happens to exist, use it" fallback — self-documenting in the scenario file, and doesn't risk a future unrelated `shared_state["users"]` entry silently changing subscription ownership.

**`harness/tasks/inference.py` (`SendRequestsTask`) changes**, both additive/backward-compatible:

- New `key_index` param: selects exactly one key from `shared_state["api_keys"]` by position as the task's single dedicated token, bypassing both `key_pool` (which always uses the *entire* pool) and the static `params.token` chain (YAML-only, can't reference a runtime-created key). Implemented by injecting the resolved key string into `self.params["token"]` before the existing single-key resolution path runs — no new resolution logic, no signature change.
- New `result_key` param (default `"inference_results"`, preserving today's behavior when unset): lets a task instance write its results to a named `shared_state` slot instead of the one fixed key every `send_requests`-family task has always shared. Necessary here because the scenario's entire point is *comparing* two sequential bursts' outcomes — the existing fixed-key overwrite (already documented in ADR-019 as acceptable *because* nothing needed to compare two runs before) would destroy the first burst's results before the second could be compared against it.
- New registry alias `REGISTRY["send_requests_as_second_user"] = SendRequestsTask`, the exact `verify_revoked_key_denied` pattern from ADR-019, purely so the second burst gets its own UI task-pipeline/progress chip instead of colliding with the first `send_requests` step's.

**New RBAC file** `deploy/rbac-user-provisioning.yaml`: a namespaced `Role`/`RoleBinding` (not cluster-scoped — `ServiceAccount`/`TokenRequest` only need to operate inside `maaspal`, unlike the CR-write RBAC files which must reach an install-specific tenant namespace) granting `create`/`delete`/`get`/`list` on `serviceaccounts` and `create` on `serviceaccounts/token`. Isolated in its own file, not folded into `deploy/rbac.yaml`, and given a prominent header comment: this is a genuinely more sensitive grant than anything else this harness holds — minting a ServiceAccount token is a real elevated capability, already flagged as such in the checklist before this file existed. It should be reviewed deliberately at apply time, not treated as routine.

**New scenario** `scenarios/rate_limit_shared_across_users.yaml`: `create_user` (2) → `apply_rate_limit_subscription` (`owner_groups: []`, `owner_users_from_shared_state: "users"`) → `provision_keys_for_users` (both keys pinned to the one subscription) → `send_requests` (`key_index: 0`, `result_key: inference_results_user_a`) → `send_requests_as_second_user` (`key_index: 1`, `result_key: inference_results_user_b`). Both bursts assert `error_rate_pct < 20`, encoding the "independent per-user allowance" hypothesis as the expected result — matching this repo's established convention (ADR-021) of treating a *surprising* assertion outcome as the actual empirical finding, not a bug report. A FAIL on `error_rate_pct_user_b` specifically (user A having already gone first) is the signal that quota is pooled/shared rather than per-user.

**No new `MaaSAuthPolicy`/`apply_auth_policy` step.** Confirmed via ADR-018's Update (live `TokenReview` output): every ServiceAccount-token caller's group list includes `system:authenticated` unconditionally, and the target cluster's pre-existing `simulator-access` `MaaSAuthPolicy` already covers that group for the standard test model. So the new users get gateway *access* for free — only *quota* eligibility needed the new per-user `owner.users` binding. This is called out explicitly as a **cluster-specific dependency**: a cluster without an equivalent pre-existing, broadly-scoped `MaaSAuthPolicy` would need this scenario to also apply one, which it currently does not.

## Consequences

**Positive:**
- Closes checklist §5 with a mechanism that actually tests what it claims (two identities, not two keys under one identity).
- Builds the exact ServiceAccount+TokenRequest mechanism ADR-018's Update already identified as the fix `access_denied_no_policy` needs — reusable there later, even though fixing that scenario is out of scope for this ADR.
- `key_index`/`result_key` are generically useful beyond this one scenario — any future scenario needing to target one specific dynamically-created key, or compare two sequential `send_requests` bursts, can reuse them with no further changes.
- The `owner_groups`/`.get()` fix closes a latent bug in three tasks at once, not just the one this scenario needed.

**Negative:**
- `ProvisionKeysForUsersTask.cleanup()` reuses `_revoke_keys(ctx)`, which deletes via `ctx.sa_token` (the harness's own admin identity), never the key's owning user's token. Whether the harness SA can actually revoke a key it didn't create is **unverified** — same honesty convention this repo applies elsewhere (e.g. ADR-018's own flagged assumptions); if it turns out the harness SA lacks this, cleanup will fail loudly (raised from `_revoke_keys`'s per-key exception handling, logged, non-fatal to the run) but leave keys orphaned.
- `token_limit`/`token_window`/`request_count` defaults in the scenario are unverified sizing guesses — need live tuning so user A's solo burst plausibly succeeds while leaving enough headroom for the comparison against user B to actually distinguish shared-vs-per-user behavior. Not yet run against a live cluster. `token_window` in particular is set to `"10m"`, deliberately much longer than the `"1s"` default other rate-limit scenarios use (that default exists to make `token_limit` directly comparable to `token_throughput_per_sec`, a comparison this scenario doesn't make) — it must outlast the *entire* scenario runtime (user minting, subscription-ready polling, both sequential bursts), not just one burst, or the window could reset between user A's and user B's traffic and produce a false "not rate-limited" result that's actually just a window reset, not evidence of a per-user allowance.
- Depends on the target cluster having a pre-existing `MaaSAuthPolicy` broadly covering `system:authenticated` (see Decision above) — a cluster without one would need this scenario extended with its own `apply_auth_policy` step first.
- Whether the `MaaSSubscription` CRD schema even accepts an empty `spec.owner.groups: []` is unverified — if the controller requires at least one owner entry, this scenario's `owner_groups: []` choice may need to fall back to a synthetic group instead.
- Minted ServiceAccount tokens default to a 3600s expiration — fine for a single run, but any future case where `apply_rate_limit_subscription`'s `_wait_for_subscription_ready` polling plus two full `send_requests` bursts somehow exceeded that window would fail requests for an unrelated reason (token expiry, not rate limiting). Not expected to matter at today's default `request_count`/`concurrency`, but worth remembering if either is raised substantially.
