# ADR-017: MaaS Cluster Visibility via Read-Only CustomObjectsApi Reads

## Status

Accepted

## Context

Kratos only ever showed information about *test runs* — scenarios, tasks, assertions, logs. It had no view of the *MaaS setup being tested*: what subscriptions exist, what quotas/rate limits they carry, which models they cover, and who can reach them. An admin had to `oc get` a handful of CRDs by hand before designing a scenario against a given cluster.

Live exploration of a real RHOAI MaaS install (`kube:admin` on `cluster-rkmhx...`) showed the richest data — `spec.priority`, `spec.owner.{groups,users}`, per-model `tokenRateLimits`, live `status.conditions` (including a `SpecPriorityDuplicate` condition that flags real misconfigurations) — lives only in the `MaaSSubscription`/`MaaSModelRef`/`MaaSAuthPolicy` CRDs, not in the MaaS REST API (`GET /v1/models` returns a much thinner shape: `id`, `url`, `ready`, `subscriptions[]` names only). Reading these CRDs cluster-wide (their namespace, e.g. `models-as-a-service`/`llm`, is install-specific and not fixed) requires RBAC the `kratos` SA doesn't have today.

See `docs/architecture/maas-domain-reference.md` for the full information catalog this ADR's reads are meant to serve, and ADR-009 for the existing (harness-side, write) use of `MaaSSubscription`.

## Decision

**Read via `kubernetes.client.CustomObjectsApi` from the API server process itself, not the harness Job.** This is standing cluster-state, not something tied to a single run — it belongs in `api/`, polled by the browser, independent of any Job lifecycle. `api/maas_client.py` is a new module, parallel to `api/k8s.py` (which manages Jobs/pods) rather than an extension of it, since the two have no logic in common beyond "call the Kubernetes API."

**Cluster-scoped `ClusterRole`, not a namespaced `Role`.** `deploy/rbac-maas-readonly.yaml` grants `get`/`list`/`watch` on `maassubscriptions`, `maasmodelrefs`, `maasauthpolicies`, `tenants`, `externalmodels` (`maas.opendatahub.io`), `tokenratelimitpolicies` (`kuadrant.io`), `limitadors` (`limitador.kuadrant.io`), `llminferenceservices` (`serving.kserve.io`), `gateways`/`httproutes` (`gateway.networking.k8s.io`), and `groups` (`user.openshift.io`) — bound cluster-wide via a `ClusterRoleBinding`, the same pattern `deploy/rbac-monitoring.yaml` already uses for `cluster-monitoring-view`. A namespaced `Role` would need to name the MaaS install's namespace explicitly, which isn't fixed across clusters; `Kubernetes serves `list_cluster_custom_object` the same way `kubectl get <plural> -A` does for a namespaced CRD, returning items across every namespace the caller can see, so a single cluster-wide grant covers every install layout without per-namespace configuration. This is read-only introspection of RHOAI's own resources (get/list/watch only, no write verbs) — consistent with the project's existing stance of acting through RHOAI's own resources rather than bypassing its access controls, not a new category of access.

**Graceful, per-resource degradation — never a hard failure.** Every read in `api/maas_client.py` returns a `ResourceList(available, items, reason)` rather than raising: a `403` (RBAC not applied) or `404` (CRD not installed — e.g. a cluster without MaaS at all, or without the `ExternalModel` tech-preview CRD) both resolve to `available=False` with a `reason`, and the caller renders whatever *is* available. This was an explicit requirement (not everyone deploying Kratos will have applied `rbac-maas-readonly.yaml`, or will be running a MaaS version with every CRD in this list) — one missing grant must degrade only the section it backs, not the entire "MaaS Setup" view, and must never affect the pre-existing Runs functionality at all. `GET /api/maas/status` exposes this per-section so the frontend can hide/warn rather than render an empty or broken table.

**Models are a merge of three sources, not a single read.** `MaaSModelRef` (CRD — display metadata, endpoint), the MaaS REST `GET /v1/models` (the only place the subscription→model reverse-index is exposed), and `LLMInferenceService` (CRD — replicas/resources/serving readiness, only fetched when a model is internally served) are combined into one shaped record per model in `list_models()`. The REST call is best-effort (`_fetch_v1_models` swallows any failure and returns an empty cross-reference) since it depends on `MAAS_API_URL`/the SA token being usable, separately from whether the CRD reads succeed. Each model also carries an explicit `hosting: "internal" | "external"` field — derived from `modelRef.kind == LLMInferenceService`, not inferred from the absence of other fields — so the UI never has to guess when a future backing kind shows up with `kind` unset. The shaped `namespace` field (already carried since the first version of this endpoint, for API purposes) is surfaced directly under the Hosting badge in `ModelsTab.tsx` — a model's namespace is where the underlying `MaaSModelRef`/`LLMInferenceService`/`ExternalModel` object actually lives, which matters for cross-checking against `oc get` output on a real cluster.

**Access Control is an all-or-nothing comparison between two sources, with a softer third.** `list_access()` (`GET /api/maas/access`) cross-references `MaaSSubscription.spec.owner.groups` (quota) against `MaaSAuthPolicy.spec.subjects.groups` (gateway access) per group, computing `quota_without_access`/`access_without_quota` model-name diffs — the two misconfiguration classes called out in the domain reference (Catalog item C). Unlike every other section here, this one can't degrade to "show what's available": the entire feature *is* the comparison, so if either subscriptions or auth policies is unreadable, the whole section reports unavailable (with that source's own reason) rather than a half-comparison that would misrepresent which model coverage is actually missing. OpenShift `Group` (`user.openshift.io/v1`, cluster-scoped) is treated as strictly softer — its absence still shows group names and the subscription/auth-policy comparison, just with `users: null` (never an empty list, which would incorrectly read as "confirmed no members") instead of resolved usernames.

**Access Control's YAML views are per-object, not per-row.** A group row can reference multiple subscriptions and multiple auth policies, so `list_access()` carries a `raw_yaml` on each subscription/auth-policy reference (reusing `list_subscriptions()`'s own `raw_yaml` for the subscription side, computing a fresh one for auth policies) plus one `raw_yaml` for the group's own `Group` CR (`None` when Groups is unavailable — used by the UI to decide whether to even offer a "View YAML" link for the group, rather than offering a link that would show nothing). In `AccessControlTab.tsx` each subscription/auth-policy chip is independently clickable, opening that specific object — there's no single "the YAML for this row" concept once a row can span several CRs.

**"View YAML" reuses the run-settings viewer, and both must stay lazy-loaded.** `RunSettingsModal`'s read-only Monaco viewer (ADR pre-dating this one; see "Frontend Monaco Setup" in CLAUDE.md) was extracted into a shared `ui/src/components/RawYamlModal.tsx`, and `api/maas_client.py` now renders a `raw_yaml` string per subscription/model via the same `yaml.safe_dump(..., sort_keys=False)` call `api/routes/config.py` already uses for run settings — so both views come from the same rendering path, not two independent YAML formatters. A model's `raw_yaml` combines its `MaaSModelRef` and (when internally served) the backing `LLMInferenceService` under `maasModelRef:`/`llmInferenceService:` keys, since debugging a serving issue usually needs both. **Caught during implementation, not anticipated up front**: initially importing `RawYamlModal` directly from `SubscriptionsTab`/`ModelsTab` pulled Monaco into the main JS bundle (confirmed via `npm run build`: main bundle jumped from ~390KB to ~3.1MB) because those tabs are reached eagerly from `App.tsx`, unlike `RunSettingsModal`, which was already behind `RunDetail.tsx`'s own `React.lazy` boundary. Fixed by giving each MaaS tab its own `React.lazy`/`Suspense` boundary around `RawYamlModal`, mirroring `RunDetail.tsx`'s existing pattern — any future direct (non-lazy) import of `RawYamlModal` will silently reintroduce this regression, so re-run `npm run build` and check for a standalone `RawYamlModal-*.js` chunk after touching either tab.

## Consequences

**Positive:**
- Genuinely richer data than the REST API alone can provide (priority, group/user ownership, per-model quotas, live reconciliation status), sourced from the same CRDs RHOAI's own MaaS controller already treats as the source of truth.
- Fails soft everywhere: no RBAC applied, an unsupported MaaS version, or a cluster without MaaS at all all resolve to a clear per-section "unavailable" state rather than a crash or an opaque 500.
- No changes to any existing harness/runner code path — this is purely additive, read-only, and lives entirely in `api/`.

**Negative:**
- A new `ClusterRole`/`ClusterRoleBinding` must be applied for this feature to show anything at all — a fresh Kratos deployment without it will show every MaaS Setup section as unavailable until an admin applies `deploy/rbac-maas-readonly.yaml` (now included in the root `kustomization.yaml`).
- `list_models()` issues one `LLMInferenceService` `get` per internally-served model in addition to the two list calls — acceptable at the scale this tool targets (a handful of test models), but not designed to scale to hundreds of models without adding caching.
- `ExternalModel`'s exact schema could not be verified live (none deployed on the research cluster) — its shaping in `list_models()` is deliberately minimal (falls back to the raw CR for anything not confirmed) rather than guessed at.
- Access Control's all-or-nothing availability means a partial RBAC grant (e.g. subscriptions readable, auth policies not) shows nothing useful for that tab even though half the data exists — an accepted trade-off since a half-comparison could actively mislead an admin about which model coverage is actually missing.

**Neutral:**
- Introduces `api/maas_client.py` as a new, independent module rather than extending `api/k8s.py` — the two share no state and are called from different route groups.
